## 1. 部署与建库（开发者工具点击路径）

- [ ] **1.1 同步镜像**：仓库根目录跑 `npm run sync:cloud`，再跑 `npm run check:cloud-sync`，输出须为「已同步、无漂移」。
- [ ] **1.2 部署云函数**：微信开发者工具 → 左侧文件树右键 `cloudfunctions/data` → **「上传并部署：云端安装依赖」**；确认右上角环境选择器 = 测试环境。
- [ ] **1.3 核对部署生效**：顶部工具栏「云开发」→「云函数」→ `data` → 看「更新时间」是否已刷新（没刷新 = 没部署上，后面的校准全是旧包）。
- [ ] **1.4 建 53 集合**：「云开发」→「数据库」→ 新建集合，对照 `docs/云开发控制台操作指南.md §2.2` 建齐 **53 个**；每个集合权限设 **「所有用户不可读写」**。
  - 校验命令：`node tools/cloud-calibration.cjs collections --json` → `missingCount` 必须为 `0`（缺任何一个，业务走到那步报 `-502005`）。
- [ ] **1.5 导入索引**：「数据库」→「索引管理」按 `docs/数据库索引清单.md` 的 112 条逐集合建立；本地 `npm run check:indexes` 通过不等于云端已建，须在控制台确认状态为「可用」。
- [ ] **1.6 初始化演示学校基础种子**：`node tools/cloud-calibration.cjs collections --seed-out <路径>` 导出 JSON（学校 2 / 学院 27 / 协会 12），在控制台按 `§3.5` 导入 `schools` / `colleges` / `school_associations` 三个集合。
  - 种子里 `buaa` 与北航学院带 `simulated: true`，仅测试样本，**不得带入生产**。
- [ ] **1.7 上传小程序**：开发者工具点「上传」填版本号；G2b 后 `CLOUD_ENV_ID` 留空会在真机 `loadSchoolMock()` 抛错，确认已填测试环境 ID。

## 2. 环境变量清单（云函数 `data` → 配置 → 环境变量）

- [ ] **2.1 必配**：
  | 变量 | 值 | 作用 |
  |---|---|---|
  | `TZ` | `Asia/Shanghai` | 云容器默认 UTC，不配会导致赛事时间窗偏移 8 小时 |
  | `CLOUD_ENV_ID`（小程序本地） | 测试环境 ID | 不在云函数配置里，在 `miniprogram/config.js` |
- [ ] **2.2 治理开关**（默认值即生产值，仅在压测/应急时改，改完记得改回）：
  | 变量 | 默认 | 何时改 |
  |---|---|---|
  | `HOME_BFF` | 开启 | `off` 降级首页旧多接口聚合（仅排障） |
  | `PRIVACY_MASK` | 开启 | `off` 关闭脱敏（仅排障，禁用于上线） |
  | `PRIVACY_MASK_PUBLIC` | `off` | `on` 加强跨校公开展示脱敏 |
  | `UGC_SAFETY` | 开启 | `off` 关闭 UGC 校验（仅排障） |
  | `UGC_WECHAT_CHECK` | `off` | `on` 接入微信 `msgSecCheck`（生产建议开启） |
  | `MAX_READ_ROWS` | `10000` | 压测时设 `500` 验证无越界全表读 |
  | `BATCH_JOB_MAX_OPS` | 默认 60 | **第 5.2 步校准后决定是否下调**（调 40 / 20） |
  | `TX_RETRY_MAX` | 默认 | `0` 一键关闭冲突重试，退回旧行为 |
  | `PARTIAL_UPDATE` | 开启 | `off` 回退整文档 set（仅排障） |
  | `SINGLE_FENCE` / `BATCH_JOB` | 开启 | `off` 回退团队赛事单栅栏 / 分批路径（仅排障） |

## 3. 真机双号测试脚本（两个微信号，A=管理员 / B=普通会员）

- [ ] **3.1 准备**：A 号设为测试学校 `schoolAdmin`，B 号仅普通在册会员；两台真机分别登录，**不要用同一个微信号切身份**（会掩盖缓存问题）。
- [ ] **3.2 权限正向**：A 号进入协会空间 → 建公告、审批入会、建赛事均成功；B 号看得到公告与榜单，但**看不到**管理入口。
- [ ] **3.3 权限反向（必测）**：B 号用开发者工具「真机调试」直接调用 `updateSchoolProfile` / 审批类写 action → 须返回业务拒绝；B 号读榜单 `realName` 应是脱敏值（如 `王*明`），不是完整实名（T-05 补的 DTO 接线）。
- [ ] **3.4 并发录分**：A、B 同时在两台真机对同一场比赛录分 → 一方成功、另一方走冲突重试后得到一致结果；云函数日志里的 `retryCount` / `errCode` 与第 5.1 步的形态一致。
- [ ] **3.5 首屏耗时**：B 号冷启动进入首页 → 云函数日志中 `getSchoolHomeSummary` 云调用为 **1 次**（不是 14–16 次）；`HOME_BFF=off` 时回退旧路径可用。
- [ ] **3.6 缓存与切号**：A 号改角色后 B 号下拉刷新 → 权限展示随之更新（多实例缓存最终一致，允许秒级延迟）；切学校/切号后旧请求不回写。

## 5. 三项真云校准（项目核心，结果用于回填常量）

> 三条命令都追加 `--json` 保存输出；脚本静态部分已自检通过，真跑需云 SDK 与测试环境。

- [ ] **5.1 事务冲突形态**：`node tools/cloud-calibration.cjs conflict --rounds 10 --json`
  - 记录 `codeHistogram`（每个 errCode 的 `count` / `sampleErrMsg` / `isRetryable`）与 `retryableHitCount`。
  - **判定**：若有冲突未命中 `isRetryable` → 把那几条 `errCode` / `errMsg` **原样**回填给 AI，扩展 `src/server/services/tx-retry.js` 的 `RETRYABLE_CODES` / `RETRYABLE_MSG_RE`；全命中则不动。
- [ ] **5.2 批任务耗时基线**：`node tools/cloud-calibration.cjs batch --ops 60 --rounds 5 --json`
  - 记录 `p50Ms` / `p95Ms` / `successRate` 与脚本给出的 `batchJobMaxOpsAdvice`。
  - **判定**：按建议决定是否把 `BATCH_JOB_MAX_OPS` 设为 `40`（P95 5–10s 或有失败）或 `20`（>10s / 成功率 <95%）；该变量是全局预算，与业务天花板取较小值，**无需改业务代码**。
- [ ] **5.3 集合与索引**：`node tools/cloud-calibration.cjs collections --json` → `missingCount=0`；控制台逐集合确认 112 条索引状态「可用」；记录真实编译包体（第 4 步）。

## 6. 结果回填给 AI（把三项产物原样贴给 AI，触发常量微调）

- [ ] **6.1** 把第 5 步三份 `--json` 输出（或截图中的 errCode / P95 / 缺失清单）**粘贴给 AI**，并说明「T-06 真云校准结果，请按规划 §6.2 回填常量」。
- [ ] **6.2** AI 据此会做且仅做三类改动：① 扩展 `tx-retry.js` 冲突码；② 调整 `BATCH_JOB_MAX_OPS` 建议值（写进指南/剧本，非硬编码）；③ 补齐缺失集合/索引声明。**任何改动都要重新 `npm test` + `npm run deploy:check` + 重新部署 `data`。**
- [ ] **6.3** 回填后在 `docs/施工切片账本.md` 把 T-06 从「AI 部分完成」改为「真云校准已通过」，并记录实测数值与提交号。

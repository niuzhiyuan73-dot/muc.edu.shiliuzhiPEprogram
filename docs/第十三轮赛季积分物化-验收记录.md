## 3 关键口径

1. **物化在会员行，不另开集合**。读端本来就要读会员行（名字、学院、在册状态），积分长在行上等于零额外读；另建「每人一行」的积分表反而多一次整表读（人数越多越贵），还多一套归属校验和一个集合。草稿先按独立集合写的，本轮推翻了。
2. **正确性靠代际，不靠「大概对」**。任何改变积分事实的写，都在**同一事务**里把 `seasons.version` +1；读端比较 `pointsSettledVersion === version`，不等就回退实时聚合。物化最多让读变慢，不会让读出错分。
3. **只写变化的人**。逐行比 `points` 与锚点：没变就不写。**0 分且从未物化过的行一个都不写**——否则首次上线要写全校会员。
4. **锚点记赛季分界点（`resetTime`）**。跨赛季的旧分不是「删掉」而是「归零并换锚点」，让行自己说明「这是哪个赛季的数」。
5. **重置赛季不做即时重算**。代际一推，读端立刻回退实时聚合，分数正确；此刻重算要把全校会员行逐行改写，等于用几百次写换一次读。旧分与旧锚点由下一次结算顺手清掉。
6. **高频写走增量，整批事实才重算**。一条训练事实固定 ±1，且归属赛季只看 `pointEffectiveAt`，所以「第 1 格加减」与「整份重算后那一格」数学等价；赛事结算一次影响一批人，仍走整次重算。
7. **已知边界**：会员行是在上次重算之后才建出来的（离校返校、审批刚通过），行上没有物化值，会读到 0，直到下一次事实写入触发重算。触发条件窄（跨校积分事实留在原校区，返校才有历史），且任何后续写都会自动对齐。

## 4 踩坑与纠正

- **草稿的独立集合方案自带写放大**。第一版把分写进 `season_points`（每人一行），读端要为此多读一次整表；更糟的是每次结算都要重写变化行，和「物化在行上」比多一个集合、多一次读、多一套范围校验。改成会员行后第 2、6 项的收益才成立。
- **`attachSchoolRepository` 会重建集合对象**。`schoolMembers.update` 一开始写在补齐循环后面、但在 `attachSchoolRepository` 之前，被它用 `{getById,set,list}` 整个盖掉——`cloud-repo-contract` 直接点名「云端仓储（顶层）缺 schoolMembers.update」。补丁必须落在它之后。
- **事务外「读整份再 set」会写回旧代际**。收尾对齐代际原来是 `readSeason()` 再 `seasons.set({...latest})`：若并发写把 version 推高，读-写之间那一小段会把 version 写回旧值，于是「已过期」被伪装成「已结算」。改成 `seasons.update({pointsSettledVersion})` 只写这一个字段。
- **直写事实的测试会读到旧物化值**。`school-training-points` 的「积分合计一致」原先直接把已结束赛事塞进仓储，绕过业务写路径，于是没有代际变化、读到旧的 1 分。这不是实现错，是测试跳过了契约步骤：补了 `bumpPointsVersion` 助手并在注释里写清「直写事实必须补代际」。
- **一行一个事务撞预算**。初版每行一次 `schoolMembers.update`（云开发上等于一行一次独立事务），176 人的双打签表就是 176 次往返，很容易吃掉 3 秒超时。改成 30 行一个事务（每行读+写 2 个操作，60 < 预算 100）。

| 项 | 原因 |

| 赛事结算改增量 | 受影响人数不定（单打 88 / 双打 176），且要处理「名次更正后不再发分」；当前整次重算每次只在结算发生一次，收益不如复杂度 |

## 8 回归与反向验证

- **反向验证「不是靠测试转绿」**：把 `pointsSettledVersion` 手工推到 version 之前，榜单仍然读 1 分且确实读了训练与签到（用例 2）——证明回退分支真的是活代码。
- **反向验证「只写变化者」**：同一事实连算两次，第二次 `written: 0` 且会员集合一次写都没有（用例 3）。
- **反向验证「不覆盖学籍」**：重算后 `collegeId` / `studentId` / `status` 原样（用例 4）。
- **反向验证「跨赛季」**：把分界推到赛事之后重算，旧分归零、锚点跟着换（用例 8）。
- **反向验证「增量等于重算」**：确认签到走增量后，行上的值与整份重算结果一致，且代际同步前进（用例 6）。

## 3 关键口径

1. **写动作的「次数」仍按次计**。`WRITE_READ_COST` 只增加读成本，不放大写次数——否则一次结算会被记成 20 次写，秒级 3 次/秒的门槛会误伤正常操作。
2. **拒绝时的提示要能解释自己**。读配额打满时写操作返回「今日读取配额已用尽（结算等操作会附带大量读取）」，而不是笼统的「操作过于频繁」——否则管理员会以为是网络或权限问题。
3. **成本值是量级估计，不是精确账单**。入口拿不到真实读条数（读完才知道）；表里取保守值，宁可少记也不误伤。真实校准要等云端压测。
4. **删死代码只删「确实无调用方」的**。`replayMembersOf` 与 `pointsFor` 全仓检索过：只剩注释与文档引用。保留 `membersOfRows`，它是现役入口。

## 4 踩坑与纠正

- **差点把「写」的语义改坏**。第一版想在 `row[kind] += ...` 里对写也乘成本点，读代码时发现那会让「结算 3 次/秒」变成「结算 0.15 次/秒」——秒级写门槛被读成本连坐。改成：读成本单独记 `row.read`，写次数仍 `+1`，并补了一条用例钉住「同一秒 3 次结算放行、第 4 次按写频率拒绝」。
- **`guardDaily` 的检查顺序变了**：现在先记读、再记写。对纯读动作行为不变（原来也是先记读），但读配额与写配额同时触顶时，返回的是读的提示——这是有意的，读才是真正的瓶颈。

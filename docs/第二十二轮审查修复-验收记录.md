## 3 关键口径

1. **名单人数不是一个 UI 数字，而是事务预算的倒数**。每人 2 次资格点读（限组再加 1 次），固定开销约 10 次；`ROSTER_LIMITS.MAX = 30` 是算出来的，不是拍的。
2. **限组资格的「在途变化」按组版本判定**。任何成员增减、退出都会推进 `group.membershipRevision`，事务内只读每个见证组一次即可；比逐人读关系行省 N 倍操作，语义不变。
3. **派生索引要么有人读、要么别写**。`sportsMeetHonors` 已无读方，停写；历史文档保留，集合与索引清单不删（避免一次性迁移）。
4. **回填巡检不挂在默认读路径上**。`rank-read-budget` 明确钉着「新库不巡检」；诊断走 `{ diagnose: true }`，部署后由管理员主动跑一次。

## 4 踩坑与纠正

- **把「添加」和「建组」当成同一个上限**：第一版把 `MAX_MEMBERS_PER_WRITE` 直接降到 28，`30 人自动分批` 的既有用例立刻红——添加是分批的，不需要收这么紧。拆成 `MAX_MEMBERS_PER_WRITE = 28`（单事务建组）与 `MAX_MEMBERS_PER_ADD = 100`（分批添加）。
- **在途退组的模拟绕过了真实写入路径**：`review20` 直接改关系行、不推进组版本，新逻辑自然判不出来。改为按真实服务语义同时 +1 `membershipRevision`，测试仍然守住「提交时资格变了就整份拒绝」。
- **榜单巡检一度加回默认路径**：`rank-read-budget` 当场变红，说明这是既定的取舍。改成显式诊断入口，既保留可观测性又不让每次榜单多付一次聚合。
